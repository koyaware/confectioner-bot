# CLAUDE.md

Источник истины: `tech.md` в корне репозитория. Прочитай его целиком перед работой. Этот файл содержит только обязательные правила. При расхождении побеждает `tech.md`.

## Проект

Telegram-бот-витрина и приемщик заказов для кондитеров (multi-tenant: один бот равно один магазин). Разработчик один. Бюджет на платные сервисы: 0.

## Контракты: не выдумывай

Схема БД (раздел 5), общие типы (7), callback-данные (8.1), джобы (8.2), статусы заказа (6), сигнатуры сервисов (8.3) заданы в `tech.md`.

- Нужного контракта, типа, поля или callback нет: остановись и выдай блок `CONTRACT GAP` (что нужно, зачем, предлагаемая форма). Код с выдуманным контрактом не пиши.
- Изменение контракта: сначала правка `tech.md`, поднятие версии и запись в changelog, затем код.
- Новые зависимости, платные сервисы, файлы на диске: только после правки `tech.md`.

## Стек

Node.js LTS (>=22), TypeScript strict, grammY (long polling, runner, auto-retry, throttler), SQLite (`better-sqlite3`, WAL) + Drizzle, zod, pino, vitest, fast-check.

## Архитектура

- `domain/`: чистые функции. Без БД, без grammY, без `Date.now()` (время приходит параметром).
- `services/`: БД и транзакции. Без Telegram.
- `bot/`: Telegram-слой. Отправка сообщений только через `TelegramPort`, никогда через grammY напрямую.
- Запись в несколько таблиц: одна синхронная транзакция.
- Статус заказа меняется только через `transition()` из `domain/order-machine.ts`.
- Все тексты бота только в `src/i18n/ru.ts`.

## Обязательные правила кода

- TypeScript: `strict`, без `any` (исключение с комментарием), `Result` вместо исключений для ожидаемых ошибок.
- zod на каждой внешней границе: env, callback-данные, payload джобов, сессия при чтении из БД.
- Деньги: целые минорные единицы (`*Minor`). Даты заказа: `IsoDate` в часовом поясе магазина, преобразования только в `lib/time.ts`.
- Любой пользовательский ввод экранируется (`domain/escape.ts`) перед подстановкой в HTML-сообщение.
- Callback-данные не длиннее 64 байт, формат `<ns>:<action>[:<arg>...]`, кодек в `bot/callbacks.ts`.
- `answerCallbackQuery` первым действием в каждом обработчике callback.
- UX: один экран равно одно сообщение (редактируй, не отправляй новое), «Назад» на каждом экране, `/start` и `/menu` сбрасывают состояние в `idle`.
- Миграции только генерируются drizzle-kit из `schema.ts`, вручную не правятся.

## Безопасность (не обсуждается)

- Токены ботов в БД только зашифрованными (AES-256-GCM, ключ `APP_SECRET`). Токены и секреты не попадают в логи и репозиторий.
- Каждый обработчик проверяет роль и принадлежность объекта: заказ, товар, категория обязаны принадлежать `ctx.tenant`. Клиент видит только свои заказы. Действия `adm:*` только для `tenant.ownerTelegramId`.
- В логах нет телефонов, адресов, текстов клиентов.
- Claim-коды одноразовые, хранятся хешем, живут 24 часа.

## Надежность

- Апдейты приходят at-least-once: обработчики и джобы идемпотентны.
- Создание заказа идемпотентно по `checkoutId`. Загрузка даты проверяется повторно внутри транзакции создания заказа.
- Джоб сначала читает актуальное состояние и выходит, если действие не нужно. Ретраи: 3 попытки (60 с, 300 с, 1800 с).
- Ошибка одного бота не останавливает остальные.

## Тесты

Тест пишется из критериев приемки задачи, не из реализации. Порядок: критерии, красные тесты, код. Тест, подтверждающий текущее поведение кода, запрещен.

На каждую задачу:
- юнит-тесты на `domain/`;
- property-based (fast-check) на инварианты: итог цены, машина статусов, загрузка даты, доступность дат, кодек callback, экранирование;
- тест идемпотентности на каждый хендлер джоба и на `chk:submit` (запуск дважды, эффект один);
- контрактные тесты: payload джобов по zod-схемам, лимиты сообщений Telegram (текст до 4096, подпись до 1024) через фейковый `TelegramPort`;
- путь ошибки через фейк (`RATE_LIMIT`, `BLOCKED`, `NETWORK`);
- сценарные тесты через `bot.handleUpdate` с фейковым портом, без сети.
