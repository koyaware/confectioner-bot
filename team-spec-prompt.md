# Мета-промпт: разбиение проекта на командную разработку

> Назначение. Ты вставляешь сюда полное ТЗ проекта (свой tech.md) и параметры команды. Нейросеть генерирует комплект файлов: общее ядро проекта + отдельные инструкции для тимлида и каждого разработчика + файл авто-подгрузки ядра. Дальше каждый кормит свой файл (вместе с ядром) своей сессии нейросети, и код собирается в одно приложение без расхождений на стыках.
>
> Как пользоваться: заполни блок «ВХОД», скопируй всё целиком в нейросеть.

---

## ВХОД (заполни перед запуском)


## РОЛЬ

Ты senior-архитектор. Разбиваешь проект на параллельную работу маленькой команды (тимлид + N разработчиков). Цель: каждый работает в отдельной сессии нейросети, пишет свой кусок, а всё собирается в одно цельное приложение и не расходится на стыках. Штат маленький, тяжёлых enterprise-процессов не нужно. Минимум трения, ничего не теряется, тимлид ни в чём не путается.

## ГЛАВНЫЙ ПРИНЦИП: единое замороженное ядро

Три сессии нейросети против трёх независимых файлов гарантированно разойдутся: разные имена типов, разные допущения о схеме БД, разные паттерны на границах. Чтобы этого не было:

- Всё общее определяется **один раз** в файле `tech.md`: стек, схема БД, контракты очереди и событий, общие TypeScript-типы, список UI-компонентов, правила кода, структура папок.
- `tech.md` **версионирован**. Сверху файла стоит номер версии и короткий changelog последних изменений (`v7 — добавлено поле order.cancelledReason`). Меняется только append-only и только тимлидом, каждое изменение контракта бампает версию. Это режет рассинхрон, когда разработчик A работает на старом ядре и не знает о новом поле.
- Каждый файл роли в начале **обязывает прочитать `tech.md`** и подчиняться ему дословно. Разработчик прикладывает `tech.md` к своему файлу в каждой сессии (или подтягивает через CLAUDE.md, см. файл №5).

Контракты (схема, типы, форматы эндпоинтов, топики очереди) принадлежат тимлиду. Разработчик их **не выдумывает**. Запрет держится на трёх уровнях, потому что текстового правила сессии мало (её работа — закрыть задачу, и не хватает поля проще выдумать):

1. **Поведенческий.** Нужного контракта нет в `tech.md` → СТОП. Сессия выдаёт блок `CONTRACT GAP` (что нужно, зачем, предлагаемая форма) и **не пишет код с выдуманным типом**.
2. **Процессный.** Разработчик открывает issue с меткой `contract-change`, продолжает работу на локальной заглушке. Тимлид аппендит контракт в `tech.md` и бампает версию.
3. **Тулинговый.** CODEOWNERS + branch protection требуют ревью тимлида на изменения `tech.md`, `lib/types`, `lib/server/db/schema`, `lib/ui`, layout. «Не трогай общие файлы» держит платформа, а не добрая воля сессии.

## ПОСЛЕДОВАТЕЛЬНОСТЬ (жёсткая)

1. Тимлид собирает и мёрджит **скелет**: репозиторий, CI/CD, каркас (layout + навигация + гард авторизации), библиотека UI-примитивов, токены дизайна, общие типы, очередь, фейковые реализации внешних клиентов за интерфейсами, транспорт реального времени (если есть live-данные), сид-скрипт, одна сквозная вертикаль end-to-end как эталон.
2. Эталонная вертикаль — это **шаблон, не пример**. Файлы разработчиков прямо предписывают: твой слайс повторяет структуру эталонного слайса в `routes/(app)/<пример>`. Рабочий пример в репо сильнее любой конвенции прозой, нейросети есть что копировать.
3. Разработчики **не начинают фичи**, пока скелет не в main и чек-лист «скелет готов» не зелёный целиком. Чек-лист конкретный, не на глаз:
   - CI зелёный на тривиальном PR;
   - layout + навигация + гард авторизации в main;
   - UI-примитивы импортируются и отрендерены в kitchen-sink роуте;
   - очередь гоняет демо-джоб;
   - транспорт реального времени эхает тестовое событие (если есть live-данные);
   - фейки внешних клиентов отдают сид-данные;
   - миграции проходят на эфемерном Postgres в CI;
   - сквозная вертикаль в main и задеплоена на тестовый VPS.
4. Файлы разработчиков дают этот чек-лист и прямо запрещают старт фич до его прохождения.

## ПРИНЦИП РАЗБИЕНИЯ: вертикальные слайсы

Режь **по фичам, не по слоям**. Не «один весь фронт, другой весь бэк» — это конфликты на стыке и вечная интеграция. Каждый разработчик владеет своей фичей целиком, сверху донизу: серверный домен (`lib/server/<домен>`) → загрузка данных и мутации (`load` / actions / `+server.ts`) → страница → её локальные компоненты. Двое почти не трогают одни файлы.

Сквозное и общее — у тимлида, собрано заранее. Назови места, где даже при вертикалях столкнутся, и отдай их тимлиду в скелет:

- навигация в layout — сделать **данными** (массив пунктов в одном файле), а не править разметку;
- реальное время (SSE/websocket) — транспорт в скелете, разработчик только подключает свой поток;
- внешние клиенты (POS, платёжка) — **интерфейс + фейк** сразу, разработчики пишут против фейка и не ждут реальных доступов;
- **миграции** — только тимлид, генерятся из схемы, применяются в деплой-шаге. Drizzle-миграции упорядочены, это точка сериализации и конфликтов, разработчики их не пишут вообще;
- **сид-скрипт** — в скелете и у тимлида, чтобы вся команда разрабатывала на одних фикстурах и фейки отдавали те же данные;
- **конфиг + `.env.example`** — единый конфиг-модуль в скелете, всё внешнее за фейками, разработчик запускается без реальных секретов.

## ТЕСТЫ: на каждый слайс

Тесты привязаны к **слайсу и PR**, не к стадии. Стадия — это несколько слайсов и несколько PR, отдельной сущности «тесты на стадию» не вводи. Слайс мёрджится только с тестами, гейт красный без них.

Главная ловушка: нейросеть пишет код, потом пишет тесты, которые подтверждают, что код делает то, что делает, вместе с багами. Тесты зелёные и ничего не проверяют. Поэтому правило: **тесты выводятся из критериев приёмки задачи, не из реализации**. Тест кодирует контракт, не зеркалит код.

Обязательные типы тестов на слайс:

- **Контрактные на стыках.** Самые ценные: джоб или событие слайса соответствует payload-схеме из `tech.md`. Фейковый клиент — это и есть тестовый шов: валидирует вход против контракта и падает, если слайс шлёт мусор.
- **Идемпотентность джобов pg-boss.** Нейросеть почти всегда пишет неидемпотентный хендлер. На каждый хендлер — тест, который гоняет его дважды с тем же payload и проверяет, что эффект ровно один. Иначе двойные списания и двойные посты в POS.
- **Путь ошибки.** Внешний клиент вернул 500, ретрай, таймаут. Проверяется через фейк, умеющий возвращать ошибку.
- **Property-based на чистой доменной логике (fast-check).** Здесь «попробуй сломать» работает буквально: генеришь входы, проверяешь инварианты.

## ЧТО СГЕНЕРИРОВАТЬ: пять файлов

### 1. `tech.md` — общее ядро (читают все)
- **Версия + changelog** сверху файла.
- Проект: что делает, для кого, цель.
- Стек целиком.
- Архитектура и структура папок (по идиомам стека).
- **Схема БД** — конкретно, в Drizzle: таблицы, поля, связи, индексы.
- **Контракты очереди и событий** — список топиков/джоб, их payload, правила идемпотентности и ретраев.
- **Общие типы** — TypeScript-типы, которые шарят несколько слайсов (`lib/types`).
- **Список UI-компонентов** — точный перечень примитивов, которые тимлид собирает заранее (Button, Table, Modal, Input, Badge, Card и т.д.), с эскизом пропсов каждого. Откуда берём базу (shadcn-svelte / Skeleton), а не пишем с нуля.
- **Стратегия тестов** — секция «ТЕСТЫ» этого промпта, дословно: тесты из критериев приёмки, контрактные на стыках, идемпотентность джобов, путь ошибки, property-based. Если сессии в Claude Code — сослаться на skill `engineering:testing-strategy`, чтобы зафиксировать подход.
- **Владение инфраструктурой** — миграции (только тимлид, из схемы, в деплое), сид-скрипт (общие фикстуры), конфиг-модуль и `.env.example`.
- Правила и конвенции кода — из входного ТЗ.
- **Конвенция коммитов, PR и комментариев** (применяют все сессии, и тимлид, и разработчики):
  - язык всего — только английский: коммиты, заголовки и описания PR, комментарии в коде;
  - **формат коммита фиксированный, всегда** Conventional Commits: `type(scope): summary`. `type` из закрытого набора `feat|fix|test|refactor|chore|docs`. `summary` в императиве, со строчной, без точки в конце, до ~50 символов, по делу. Тело коммита только если нужно объяснить *почему*, не *что*;
  - **сессия коммитит сама по ходу работы**, маленькими логическими коммитами после каждого осмысленного шага, не сваливает всё одним коммитом в конце. Каждый коммит по возможности проходит тайпчек;
  - PR: заголовок краткий и содержит ID issue Linear (для авто-связи ветки → PR → issue), тело короткое и понятное — что делает слайс, какие контракты и типы затрагивает, чем покрыт тестами;
  - **комментарии в коде** кратко и по делу, объясняют *почему*, а не пересказывают очевидный код; закомментированный код в PR не оставлять;
  - дисциплина `stop-slop` действует на всю эту прозу: активный залог/императив, без em-dash, без филлеров.
- **Definition of Done одной задачи**: линт, тайпчек, build, привязанная задача, и тесты по доктрине выше (выведены из критериев приёмки; для каждого джоба — тест идемпотентности; на стыках слайсов — контрактный тест).
- Дорожная карта по стадиям.

### 2. `LEAD.md` — для тимлида
- CI/CD: разделить **гейт на PR** (svelte-check, eslint+prettier, vitest/Playwright, build, миграции на эфемерном Postgres, без деплоя) и **деплой на мёрдж в main** (на тестовый VPS, миграции в деплой-шаге). Branch protection на main: только через PR, мёрдж при зелёном CI.
- **CODEOWNERS + branch protection** на общие файлы: `tech.md`, `lib/types`, `lib/server/db/schema`, `lib/ui`, layout. Любая правка этих путей — только через ревью тимлида.
- Порядок сборки скелета: что заскаффолдить и смёрджить **до** раздачи задач. Финальный пункт — пройти чек-лист «скелет готов».
- Список компонентов под пред-сборку (из `tech.md`).
- Какие контракты заморозить в начале.
- **Миграции**: генерить из схемы, применять в деплой-шаге, в PR-гейте прогонять на эфемерном Postgres.
- **Сид-скрипт** в скелете, общий для всей команды и фейков.
- **Обработка `CONTRACT GAP`**: получил блок от разработчика → аппендит контракт в `tech.md` → бампает версию → закрывает issue `contract-change`.
- **Long-lead вещи запустить в день один** (из блока ВХОД), параллельно разработке.
- Транспорт реального времени в скелет.
- Фейковые клиенты внешних сервисов за интерфейсами.
- **Чек-лист ревью PR** (механический, проходить по каждому пункту):
  - нет выдуманных типов, всё из `tech.md`;
  - не тронуты чужие домены и общие файлы;
  - тесты проверяют контракт, а не реализацию;
  - использованы UI-примитивы вместо самописного UI;
  - для каждого джоба есть тест идемпотентности;
  - на стыке слайса есть контрактный тест.
- Если сессии в Claude Code — сослаться на skills `engineering:code-review` (чек-лист ревью) и `engineering:architecture` (ADR на решения по контрактам и слайсингу).

### 3. `DEV_A.md` и `DEV_B.md` — для разработчиков
Для каждого:
- Блок «Прочитай первым»: подчиняйся `tech.md`, прикладывай его к каждой сессии (или подтягивай через CLAUDE.md), контракты не выдумывай.
- **Блок `CONTRACT GAP`**: не хватает контракта/типа/поля → СТОП. Выдай блок: что нужно, зачем, предлагаемая форма. Код с выдуманным типом не пиши. Открой issue `contract-change`, продолжай на локальной заглушке, жди апдейта `tech.md` от тимлида.
- **Эталон**: твой слайс повторяет структуру эталонного слайса в `routes/(app)/<пример>`. Сверяйся с ним, не изобретай свою раскладку.
- Что владеет: его серверные домены + его роуты (целиком — бэк-логика и UI этой фичи у него).
- Стадийный список задач: **каждая задача = один вертикальный слайс = один PR** («POS: синк меню и стоп-листа раз в 15 мин в БД», «Панель: страница Заказы со статусами и фильтром»), не «сделать бэкенд».
- **Тесты на слайс** (по доктрине из `tech.md`): из критериев приёмки задачи; для джоба — тест идемпотентности; путь ошибки через фейк; чистая логика — property-based. PR без тестов не проходит гейт. Если сессии в Claude Code — сослаться на skill `engineering:testing-strategy`.
- Какие готовые компоненты и контракты использовать (ссылки внутрь `tech.md`).
- Рабочий цикл задачи: ветка из задачи → коммиты по ходу → PR → CI → ревью тимлида → мёрдж → автодеплой. Коммиты, PR и комментарии — по конвенции из `tech.md` (английский, фиксированный формат коммита, маленькие коммиты по ходу, ID issue в заголовке PR).
- Что НЕ трогать: чужие домены и общие файлы (примитивы, layout, схема, типы). **Миграции не пишет вообще.** Сквозные правки — через тимлида.

### 4. `CLAUDE.md` — авто-подгрузка ядра (если сессии в Claude Code)
- Лежит в корне репо. Ссылается на `tech.md` и на файл роли, чтобы ядро подтягивалось в каждую сессию автоматически.
- Снимает хрупкую зависимость «разработчик забыл приложить `tech.md`».
- Короткий: указатель на `tech.md` (источник истины) + правило «подчиняйся ему дословно, контракты не выдумывай, при нехватке — `CONTRACT GAP`».

## ПРАВИЛА ДЛЯ ФАЙЛОВ РАЗРАБОТЧИКОВ

- Файл самодостаточен для старта сессии, но всегда поверх `tech.md`.
- Нейросеть реализует **одну задачу за раз** из стадийного списка, отдаёт сфокусированный дифф, не вываливает всё приложение сразу. Это бережёт ревью тимлида.
- Каждая задача описана: цель, какой домен/роут, какие контракты и типы затрагивает, какие UI-компоненты использует, критерии приёмки, какие тесты пишутся (из критериев).
- Не хватает контракта — `CONTRACT GAP`, не выдумывание.
- Разработчик не редактирует чужой домен, общие файлы и миграции.

## СТИЛЬ ФАЙЛОВ

Сухо, технично, конкретно. Без вводных оборотов, без маркетинга, без воды, без эмодзи. Императив и точные формулировки. Примеры путей и имён — из заданного стека. Соблюдай ту же дисциплину письма, что и в исходном ТЗ, и конвенцию skill `stop-slop`: активный залог, конкретика вместо общих фраз, без филлеров.

## ПРОЦЕСС

1. Прочитай ТЗ из блока ВХОД.
2. Выведи архитектуру, границы слайсов, список UI-компонентов и контракты.
3. **Сначала покажи короткий «план разбиения»**: границы слайсов, кто чем владеет, перечень компонентов под пред-сборку, замороженные контракты с номером версии ядра, чек-лист «скелет готов», подход к тестам по слайсу. Одним экраном, чтобы тимлид утвердил с одного взгляда.
4. После подтверждения сгенерируй пять файлов, согласованных с `tech.md` (`tech.md`, `LEAD.md`, `DEV_A.md`, `DEV_B.md`, `CLAUDE.md`).
